[Item 8. finalizer와 cleaner 사용을 피하라]()

자바가 제공하는 두 가지 객체 소멸자

자바 9에서 `finalizer`는 `depreacted` API로 지정하고 `cleaner`를 대안으로 소개함.

C++의 `destructor`와는 다른 개념이다.

자바에서 접근할 수 없게 된 객체를 회수하는 역할은 garbage collector의 몫

자바에서 C++의 `destructor`와 비슷한 용도는 `try-with-resources`, `try-finally`를 사용

- `finalizer`, `cleaner`는 즉시 수행된다는 보장이 없어 예측할 수 없다.
- 제때 실행되어야 하는 작업은 절대 할 수 없다.
- `finalizer`, `cleaner` 실행 시점은 garbage collector 알고리즘에 따라 달려있다.
- `cleaner`는 `finalizer`와는 다르게 자신을 수행할 스레드를 제어할 수 있다.
- 둘 다 수행 여부조차 보장하지 않는다.

따라서, 상태를 영구적으로 수정하는 작업에서는 절대 `finalizer`, `cleaner`에 의존하면 안된다.

`System.gc`, `System.runFinalization` 메소드를 신뢰하지 말자.

`finalizer`, `cleaner` 실행 가능성은 높여주지만 보장하진 않는다.

`System.runFinalizersOnExit`, `Runtime.runFinalizersOnExit`는 호출을 보장하는 함수지만 `ThreadStop` 결함 때문에 수십 년간 지탄 받아옴


`finalizer` 동작 중 발생한 예외는 무시되며, 경고조차 출력하지 않는다.

처리할 작업이 남아있어도 그 순간 종료된다.

`cleaner`는 자신의 실행 스레드를 통제하기 때문에 이러한 문제는 발생하지 않는다.

둘 다 객체 생성, 파괴 시점을 기준으로 보면 `try-with-resources` 보다 성능이 떨어진다.

`finalizer`를 사용한 클래스는 `finalizer` 공격에 노출되어 보안 문제를 일으킬 수도 있다.

종료해야할 자원을 담고 있는 객체의 클래스에서는 `AutoCloseable`을 구현하고 `close` 메소드를 호출해주는 방법이 대안

`try-with-resources`를 사용하면 예외가 발생해도 제대로 종료가 된다.


`finalizer`, `cleaner`는 자원 회수의 안전망 역할정도로 사용하자

`close`를 통한 명시적인 자원 회수 처리가 누락된 경우 늦은 자원 회수를 하도록 유도할 수 있다.

garbage collector가 감지할 수 없는 네이티브 코드를 사용하는 객체에서 자원 회수 용도로 사용하자

단, 성능 저하를 감당할 수 있고 네이티브 피어가 심각한 자원을 가지고 있지 않을 때만 해당된다.

즉시 회수해야 한다면 `close` 메소드를 구현해 사용하자.

> 불확실성, 성능 저하에 주의하고 안전망 역할이나 중요하지 않은 네이티브 자원 회수용으로만 사용하자.


[Item 9. try-finally보다는 try-with-resources를 사용하라]()

`close` 메소드를 호출해 직접 회수해야하는 클래스들이 있다.

`close`를 호출을 보장하는 수단으로 `try-finally`를 많이 사용해왔다.

다만, `close`를 호출해야할 객체가 여러개 일 경우 `try-finally` 블록이 늘어나 코드가 지저분해진다.

예외는 `fianlly` 블록에서도 발생할 수 있기 때문에 예외가 꼬여 스택 추적을 어렵게 만드는 원인이 되기도 한다.

자바 7에서는 이런 문제를 해결하기 위해 `try-with-resources`를 제공한다.

사용하기 위해선 `AutoCloseable` 인터페이스를 구현해줘야한다.

`close` 호출 양쪽에서 예외가 발생해도 스택 추적 내역에 숨겨졌다는 표시가 되므로 추적이 가능하다.

[Item 10. equals는 일반 규약을 지켜 재정의하라]()

다음에서 열거한 상황 중에 해당하면 재정의 하지 말자.

- 각 인스턴스가 본질적으로 공유하다
- 인스턴스의 '논리적 동치성(logical equality)'을 검사할 일이 없다.
- 상위 클래스에서 재정의한 `equals`가 하위 클래스에도 딱 들어 맞는다.
- 클래스가 `private`이거나 `package-private`이고 `equals` 메소드를 호출할 일이 없다.

실수로라도 호출되는걸 막고 싶으면 다음과 같이 재정의 후 `assert` 예외를 발생 시키자.

```java
@Override public boolean equeals(Object o) {
    throw new AssertionError();  // 호출 금지
}
```

- 값을 가지는 클래스 같이 논리적 동치성을 확인해야 하는 경우 `equals`를 재정의하자.
  - 다만, 값이 같은 인스턴스가 둘 이상 만들어지지 않음을 보장한다면 예외


[Item 11. equals를 재정의하려거든 hashCode도 재정의하라]()

- equals를 재정의한 클래스 모두에서 hashCode도 재정의해야 한다.
- equals만 재정의하면 HashMap, HashSet 같은 컬렉션의 원소로 사용할 때 문제를 일으킨다.

> Object 명세 중 규약  
  equals(Object)가 두 객체를 같다고 판단했다면, 두 객체의 hashCode는 똑같은 값을 반환해야한다.

- 해시 충돌을 고려해 구현하자.
- 해시 성능, 품질을 고려해 구현하자.

실수했다면 컴파일러가 알려줄 것이다.

[Item 41. 정의하려는 것이 타입이라면 마커 인터페이스를 사용하라]()

마커 어노테이션과는 다르게 마커 인터페이스는 이를 구현한 클래스의 인스턴스들을 구분하는 타입으로 쓸 수 있다.


## 7장. 람다와 스트림

[Item 42. 익명 클래스보다는 람다를 사용하라]()

- 익명 클래스 방식은 코드가 너무 길어진다.
- 람다식은 코드가 훨씬 간결해지고 동작이 명확하게 드러난다.

- 타입을 명시해야 코드가 더 명확할 때만 제외하고는 람다의 모든 매개변수 타입은 생략하자

- 람다는 이름이 없기 때문에 문서화를 할 수가 없다.
- 코드 자체로 동작이 명확히 설명되지 않거나 코드 줄 수가 많아지면 람다를 쓰지 말아야 한다.

[Item 43. 람다보다는 메서드 참조를 사용하라]()

람다는 익명 클래스에 비해 간결함을 가지고 있다.

메서드 참조로 구현하면 람다보다도 더 간결하게 만들 수 있다.

> 메소드 참조와 람다 중 짧고 명확한 쪽을 사용하자

[Item 44. 표준 함수형 인터페이스를 사용하라]()

- 직접 구현하지 말고 표준 함수형 인터페이스를 최대한 활용해라
- 직접 구현한 함수형 인터페이스에는 항상 `@FunctionalInterface` 어노테이션을 사용하자

[Item 45. 스트림은 주의해서 사용하라]()

다량의 데이터 처리 작업을 돕고자 자바 8에 추가된 API

- 과하게 사용하면 코드 가독성이 나빠진다. 

다음과 같은 상황일 때 사용하면 좋다.

- 데이터를 일관되게 변환
- 데이터를 필터링
- 데이터를 하나의 연산을 사용해 결합
- 데이터를 컬렉션에 모은다
- 특정 조건을 만족하는 데이터를 찾는다.

> 스트림과 반복 중 어느 쪽이 나은지 확신하기 어렵다면 둘 다 해보고 나은 쪽을 선택


[Item 46. 스트림에서는 부작용 없는 함수를 사용하라]()

스트림은 함수형 프로그래밍에 기초한 패러다임

스트림이 제공하는 표현력, 속도, 병렬성을 얻으러면 패러다임까지 함께 받아들여야 한다.

- 다른 가변 상태를 참조하지 않는다.
- 함수 스스로도 다른 상태를 변경하지 않는다.

`forEach` 연산은 스트림 계산 결과를 보고할 때만 사용하고, 계산하는 데는 쓰지 말자

- 수집기: toList(), toSet(), toCollection(collectionFactory), toMap()
- comparing 비교자 생성 메서드


[Item 47. 반환 타입으로는 스트림보다 컬렉션이 낫다]()

스트림은 iteration을 지원하지 않는다.

`Iterable` 인터페이스를 형 변환하여 사용할 수는 있으나 코드가 난잡해지고 직관성이 떨어진다.


[Item 48. 스트림 병렬화는 주의해서 적용하라]()

데이터 소스가 Stream.iterate거나 중간 연산으로 limit를 쓰면 파이프라인 병렬화로는 성능 개선을 기대할 수 없다.

잘못 병렬화하면 성능이 나빠질 뿐만 아니라 결과 자체가 잘못되거나 예상 못한 동작이 발생할 수 있다.

- 가변인수 메서드는 호출될 때마다 배열을 새로 하나 할당하고 초기화한다.
- 호출 빈도가 많은 인수의 개 수가 있다면 미리 정의를 하고나서 이후에 가변인수 메서드를 호출하도록 하자


[Item 54. null이 아닌, 빈 컬렉션이나 배열을 반환하라]()

컬렉션을 반환할 때 빈 컬렉션일 경우 null을 반환하게 되면 호출하는 쪽에서 null 체크 처리를 해주어야 한다.

방어 코드를 빼먹으면 오류 발생 가능성이 있다.


[Item 55. 옵셔널 반환은 신중히 하라]()

- 옵셔널을 반환하는 메서드는 예외를 던지는 메서드보다 유연하고 사용하기 쉽다.
- null을 반환하는 메서드보다 오류 가능성이 적다.

- 옵셔널을 반환하는 메서드에서는 절대 null을 반환하지 말자.

- 컨테이너 타입은 옵셔널로 감싸지 말고 빈 컨테이너를 반환하자
- 결과가 없을 수 있으며, 클라이언트가 이 상황을 특별하게 처리해야 한다면 `Optional<T>`를 반환한다.
- 박싱된 기본 타입을 담은 옵셔널을 반환하지 말자.
- 옵셔널을 컬렉션의 키, 값, 원소나 배열의 원소로 사용하는 적절한 상황은 없다. 절대 쓰지말자

[Item 64. 객체는 인터페이스를 사용해 참조하라]()

- 적합한 인터페이스가 없다면 당연히 클래스로 참조해야 한다.

- 성능이 떨어진다.

인스턴스 생성에만 쓰고, 만든 인스턴스는 인터페이스나 상위 클래스로 참조해 사용하자.

[Item 81. wait와 notify보다는 동시성 유틸리티를 애용하라]()

- `java.util.concurrent`
  - 실행자 프레임워크
  - concurrent collection
  - synchronizer

- List, Queue, Map 같은 표준 컬렉션 인터페이스에 동시성을 가미해 구현한 고성능 컬렉션
- 동시성 컬렉션에서 동시성을 무력화하는 건 불가능하며, 외부에서 락을 추가로 사용하면 오히려 속도가 느려진다.

- Collections.synchroizedMap 보다는 ConcurrentHashMap을 사용하는게 훨씬 좋다.


[Item 82. 스레드 안정성 수준을 문서화하라]()

- 메서드 선언에 synchronized 한정자를 선언할지는 구현 이슈일 뿐 API에 속하지 않는다.
- 멀티 스레드 환경에서도 API를 안전하게 사용하게 하려면 클래스가 지원하는 스레드 안정성 수준을 정확히 명시해야 한다.

- immutable
- unconditionally thread-safe
- conditionally thread-safe
- not thread-safe
- thread-hostile

스레드 안정성 어노테이션

- `@Immutable`
- `@ThreadSafe`
- `@NotThreadSafe`


[Item 83. 지연 초기화는 신중히 사용하라]()

대부분의 상황에서 일반적인 초기화가 지연 초기화보다 낫다.

성능 때문에 정적 필드를 지연 초기화해야 한다면 지연 초기화 홀더 클래스(lazy initialization holder class) 관용구를 사용하자.

성능 때문에 인스턴스 필드를 지연 초기화해야 한다면 이중검사(dubole check) 관용구를 사용하라.


[Item 84. 프로그램의 동작을 스레드 스케줄러에 기대지 말라]()

- 정확성이나 성능이 스레드 스케줄러에 따라 달라지는 프로그램이라면 다른 플랫폼에 이식하기 어렵다.

- 스레드는 당장 처리해야 할 작업이 없다면 실행되서는 안 된다.
- 스레드 busy waiting은 프로세서에 큰 부담을 준다
- Thread.yield를 써서 문제를 고쳐보려는 유혹을 떨쳐내자

[Item 87. 커스텀 직렬화 형태를 고려해보라]()

- 먼저 고민해보고 괜찮다고 판단될 때만 기본 직렬화 형태를 사용하라
- 객체의 물리적 표현과 논리적 내용이 같다면 기본 직렬화 형태라도 무방하다
- 불변식 보장과 보안을 위해 readObject 메서드를 제공해야 할 때가 많다.

객체의 물리적 표현과 논리적 표현의 차이가 클 때 기본 직렬화 형태를 사용하면 크게 네 가지 면에서 문제가 생긴다.

1. 공개 API가 현재의 내부 표현 방식에 영구히 묶인다.
2. 너무 많은 공간을 차지할 수 있다.
3. 시간이 너무 많이 걸릴 수 있다.
4. 스택 오버플로를 일으킬 수 있다.
